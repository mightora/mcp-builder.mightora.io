START WITH A PURPOSE

What will your server do?

A server is a collection of named tools your chosen AI client can discover and call.

✦
Why start with intent?

Small, purposeful tools are easier to understand, secure and test than one unrestricted database query tool.

DESIGN THE CAPABILITIES

Choose the tools to expose

Select exact Dataverse entity sets and fields. This release generates read-only search and record retrieval tools.

⚑
Dataverse logical names matter.

Use logical field names such as accountnumber and the exact entity set name, often accounts. Avoid display labels.

IDENTITY AND AUTHORISATION

Whose permissions should apply?

Your MCP endpoint authenticates callers first. A separate identity is then used when the server accesses Dataverse.

02 / HOW IT WORKS

MCP is an integration boundary.
Not a security bypass.

An AI assistant is a presentation layer. The custom MCP server publishes carefully defined capabilities; Dataverse continues to enforce its own permissions.

01
✳

ChatGPT, VS Code, Copilot Studio or another supported MCP host interprets the request and presents the answer.

03 / TRUST BY DESIGN

Permissions are not a prompt.

Your AI assistant cannot grant itself Dataverse privileges. The server has to enforce every operation.

◉

Delegated user context

When the host supports Entra OAuth, the Function obtains a separate Dataverse token using OBO. User-level access applies end to end.

Read Microsoft's OBO guidance ↗
▣

Application context

A dedicated Dataverse application user receives explicit roles. MCP callers still require authentication and per-tool controls.

Understand Dataverse OAuth ↗
⚑

Fail closed

No arbitrary SQL or OData expressions, no default write actions, no unbounded results and no credentials committed to source control.

Review your tool definition ↗
Important: Azure Functions' built-in MCP OAuth is documented by Microsoft as a preview capability. Review the supported client and tenant configuration before using a generated server in production.

04 / DEPLOY WITH CONFIDENCE

A guided path from YAML to production.

The exported project contains a deployment guide, security review checklist and tests. Configure the environments once, then promote the same build through your ALM pipeline.

1
Make a feature branch

Edit the YAML visually, import it back into the builder or review changes in Git.

2
Validate and review

Build, security checks, schema validation and pull request approval.

3
Deploy to development and test

Configure separate Function Apps and Dataverse environments. Test both valid and denied access.

4
Approve production

Deploy the verified artefact with a human approval and retain a rollback path.

What you'll need

Azure subscription, Dataverse environment, Entra permissions, and a GitHub or Azure DevOps repository.

How you'll test

Use MCP Inspector, a supported host and restricted test identities to check security boundaries.

What you own

The YAML, generated source, Azure resources, access controls and complete deployment history.

05 / PRIVACY AND TRANSPARENCY

Your design stays yours.

The builder processes your server definition in your browser and saves it locally on this device. It does not request Dataverse credentials or send your table definitions to Mightora.

The online edition loads Mightora's shared interface assets. The downloadable offline edition embeds its assets and works without an internet connection.
